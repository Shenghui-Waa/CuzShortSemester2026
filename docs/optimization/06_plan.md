# 06 聊天与 WebSocket 可靠性

## 现状与问题

WebSocket 配置允许任意 Origin，连接通过 query token 认证且主要用于通知；联系人查询存在从消息表全量加载后在 Java 聚合的倾向。当前需要明确断线重连、重复通知、消息顺序、在线状态和异常监控策略。

## 目标

连接来源和身份可控，消息具备可靠投递语义，历史查询可分页，系统能发现连接和推送故障。

## 实施方案

1. 使用可信 Origin 白名单；优先通过握手 header/cookie 传递 token，避免 token 出现在 URL 日志中。
2. 建立连接鉴权、心跳、空闲超时、最大连接数和单用户多设备策略。
3. 消息写库成功后再推送，使用 message id、客户端 ack、去重和断线补发标记。
4. 历史消息按会话和时间游标分页；未读数、最后消息和联系人聚合下推到 SQL。
5. 对内容长度、发送频率、会话参与者和商品关联做服务层校验，保留 AES 加密和密钥轮换设计。
6. 增加连接数、发送失败、重连次数、消息延迟和积压指标。

## 改动范围

WebSocketConfig、ChatWebSocketHandler、ChatService/Mapper/XML、聊天表索引、前端 ChatView 与连接封装。

## 验收标准

- 非白名单 Origin 和无效身份无法建立有效会话。
- 断线重连后未读消息不丢失且不重复展示。
- 联系人和历史消息查询不做全量内存加载。
- 指标能定位认证失败、推送失败和延迟异常。

## 风险与回滚

客户端升级期间保留旧握手协议但限制有效期；消息 ack 字段可先后向兼容，不立即删除旧字段。
