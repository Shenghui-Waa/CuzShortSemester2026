# 03 API 权限与接口契约统一

## 现状与问题

SecurityConfig 放行 `/api/announcement/**`，而控制器使用 `/api/announcements`，导致公开公告接口可能被错误要求认证。商品删除路径存在 `/del` 形式，前端 API、控制器和文档存在契约漂移风险。权限规则集中在字符串匹配中，缺少自动化矩阵验证。

订单详情服务虽然接收当前用户 ID，但当前查询链路需要重点修复为“订单 ID + 参与者”联合约束；否则登录用户可能通过枚举订单 ID 读取非本人订单。多个 Controller 还会自行解析 Authorization，与 Spring Security 已建立的认证上下文形成双重身份来源。

## 目标

资源命名、HTTP 方法、响应结构和权限规则统一，并由契约测试持续约束。

## 实施方案

1. 以 OpenAPI 或统一接口清单为唯一来源，确定复数资源路径、请求 DTO、错误码和分页格式。
2. 将商品删除规范为 `DELETE /api/products/{id}`，保留旧路径短期兼容并记录弃用时间。
3. 修正公告公开路径，并按 GET/写操作和角色拆分权限规则；禁止宽泛 `/**` 放行覆盖敏感资源。
4. 对管理员操作增加服务层所有权/角色校验，不能只依赖 SecurityConfig。
5. 订单详情、商品修改、聊天和个人资源查询均使用资源 ID 与当前用户 ID 联合查询；管理员使用独立用例，服务层再执行参与者校验。
6. Controller 统一通过 `SecurityContext` 或 `@AuthenticationPrincipal` 取得身份，删除手工截取 Bearer token 的重复逻辑。
7. 所有写接口使用专用 Command DTO 和 Bean Validation，禁止直接绑定数据库 Entity，并限制分页大小和枚举值。
8. 为公开、普通用户、资源所有者、管理员四类角色建立参数化 API 权限测试。

## 改动范围

后端 Controller、SecurityConfig、Service 授权方法；前端 API 封装；OpenAPI/接口文档和测试。不改变业务语义，只统一契约。

## 验收标准

- 公告列表和详情无需登录，公告管理必须管理员登录。
- 普通用户无法读写他人商品、订单、聊天和个人资源。
- 枚举其他订单 ID 返回 403 或防枚举的 404，不泄露订单内容。
- 前端所有请求路径与后端映射一致，旧路径有明确 410/弃用策略。
- 权限矩阵测试在 CI 中稳定通过。

## 风险与回滚

路径变更可能影响已发布前端。先增加兼容映射和响应头提示，再按版本移除旧接口。
