# 07 数据访问与数据库性能

## 现状与问题

项目使用 MyBatis 注解与 XML 混合方式，部分列表已分页，但聊天联系人聚合、热点商品和分类查询仍可能重复访问数据库。`user` 表名存在兼容性风险，索引、慢查询、连接池和分页上限未形成统一治理。

## 目标

查询在数据库侧完成过滤和聚合，关键路径有合适索引和上限，SQL 可观测且跨环境兼容。

## 实施方案

1. 盘点所有列表和关联查询，输出 SQL、调用方、分页方式、最大页大小和索引需求清单。
2. 为商品筛选、订单用户状态、聊天会话时间、未读消息、收藏购物车唯一键建立复合索引，并用 EXPLAIN 验证。
3. 将联系人、未读数、分类商品数等聚合下推 SQL，避免 N+1 和全量 Java 聚合。
4. 对分类、首页商品等热点只读数据增加可失效缓存；缓存失效与管理写操作绑定。
5. 统一分页插件和响应模型，限制 pageSize，禁止客户端通过 offset 读取超大页；必要时采用游标分页。
6. 评估将 `user` 重命名为 `users` 或统一转义，并建立迁移脚本和回滚脚本。
7. 引入 Flyway 等版本化迁移工具，为唯一键、外键、状态约束和复合索引提供可重复的基线与增量脚本。

## 改动范围

Mapper/XML、SQL migration、Service 查询策略、缓存适配层、连接池和慢查询日志配置。

## 验收标准

- 关键列表 EXPLAIN 使用目标索引，慢查询有阈值告警。
- 联系人和首页查询内存占用随结果页大小增长，而非随总数据量增长。
- 缓存命中、失效和降级均有指标。
- MySQL 8 初始化和升级迁移在干净数据库、历史数据库均通过。
- CI 同时验证空库初始化和上一版本数据库升级，不允许手工漂移 schema。

## 风险与回滚

缓存引入短暂脏读，先只用于公开只读数据；表重命名采用双写/视图兼容窗口，确认无旧 SQL 后再切换。
