# 04 订单状态机与交易一致性

## 现状与问题

订单创建已有事务和商品行锁，但支付为直接改状态的模拟逻辑，状态流转、重复请求、超时取消和价格快照仍需统一约束。支付、发货、确认和取消采用普通查询后更新时，竞争请求可能互相覆盖。评价创建还需要校验订单已完成、评价目标为订单另一参与者，并防止并发重复评价和信誉分更新丢失。

## 目标

订单状态只能按显式状态机转移；库存、价格、金额和订单事件可审计；重复请求不会重复扣减或重复推进状态。

## 实施方案

1. 定义状态转移表和每个动作的操作者、前置条件、幂等键及错误码。
2. 创建订单时锁定商品行，写入订单项价格快照；使用唯一业务订单号和请求幂等键。
3. 支付接口改为支付意图/回调模型；真实支付接入前明确模拟支付仅限开发 profile。
4. 发货、收货、取消和超时任务统一走状态机服务，使用条件更新防止并发覆盖。
5. 增加订单状态历史表和领域事件，记录操作者、时间、来源和前后状态。
6. 评价创建纳入事务，校验订单状态、评价人、目标用户和评分范围；增加 `UNIQUE(order_id, reviewer_id)`。
7. 信誉分使用数据库原子增量并设置上下限；唯一键冲突转换为稳定业务错误。
8. 设计库存恢复、支付回调重试和异常补偿流程，所有外部回调必须验签。

## 改动范围

OrderService、Mapper/XML、订单表及迁移、支付适配层、后台接口和前端状态展示。需要补充定时任务或消息组件时先评估现有基础设施。

## 验收标准

- 非法状态转换返回稳定错误码。
- 同一幂等请求重复提交只产生一个订单结果。
- 并发购买同一商品最多一个成功，失败事务不残留购物车/订单项。
- 同一用户对同一订单并发评价最多一条成功，信誉分无丢失更新。
- 每次状态变化可追溯，模拟支付在生产启动时被拒绝。

## 风险与回滚

历史订单可能存在旧状态。迁移前建立状态映射和备份；新状态机先对新订单启用，旧订单提供只读兼容处理。
